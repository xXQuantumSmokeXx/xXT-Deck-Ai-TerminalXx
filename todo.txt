[x] CHAT WITH A PERSONA, TOKEN AND CODE — WORKING, TESTED ON THE DEVICE (2026-10-18).
    The chat path was verified working on the T-Deck itself, not just built. The earlier
    ngrok TLS EOF in serial-live.log (14:57) was the known ngrok-on-ESP32 handshake failure,
    not a chat or credential fault; over the portal's LAN address the round-trip completes.
    Treat ngrok as unusable from this device and keep server_url on the LAN address.

    WHAT SHIPPED (built, flashed, tested):
      * chat.cpp sends {"message": "...", "agent_context": {"personality_profile": "..."}}
        and no longer sends `system` or `context` — a payload the server dropped was a trap
        for the next reader;
      * PersonaDef gained `profile`, read from a "profile: <name>" line anywhere in the card
        and never sent to the server; p1.txt carries "profile: Standard", p2/p3 document the
        line. Missing or unknown -> Standard, matching the server;
      * the request carries X-Portal-Token and X-Commander-Code when each is loaded from the
        SD card (portal_token.txt / commander_code.txt) or stored with settoken / setcode;
        setcode and the credential guard landed at 14:11;
      * chat logs url=..., assist=..., token=<len>, code=<len>, and the HTTP error on every
        attempt, so an absent credential or a dead tunnel is visible instead of silent;
      * .gitignore covers the SD-card credential and content files, so a broad `git add`
        cannot sweep them in.

    SERVER HALF: MayDay-AI/todo.txt, "T-DECK AI CHAT — THE SERVER HALF" (done 2026-10-18).
    /simple honours agent_context.personality_profile, accepts only the four built-ins
    (Standard, Tactical, Relaxed, Maximum Sass), falls back to Standard for anything else,
    and ignores the SD card's free-text `system`. README.md documents the two credentials,
    settoken and setcode.

    DO NOT "just switch endpoints": /chat and /chat_text are multipart + SSE, stream base64
    WAV the device would discard, and (through the portal) would make the device carry a PIN
    it currently, and deliberately, does not need. /v1/chat/completions is JSON-shaped and
    would suit the firmware, but it ignores a client-supplied system prompt, the portal does
    not proxy it, and it would need a direct brain URL plus a PIN. The small fix was the
    right one, and it is already in.

    CONTEXT, NOT A PROBLEM HERE: the phone app posts to /chat_text, which already accepts
    agent_context — only the T-Deck door could not carry a persona, and now it can.
